# 02. Архитектура плейса и фичи

## Принципы, из которых выводится всё остальное

1. **Сервер объявляет, клиент показывает.** Сервер не проигрывает музыку и не двигает свет.
   Он рассылает только «трек X стартует в момент T по общим часам». Вся картинка собирается
   на клиенте, поэтому трафик во время шоу почти нулевой.
2. **Мастер-часы — позиция внутри трека.** Свет, пиро и экраны привязаны к `Sound.TimePosition`,
   а не к серверным тикам. Если клиент подлагнул и музыка уехала, картинка уедет вместе с ней
   и останется синхронной.
3. **Деньги и доступ — только на сервере.** Клиент может лишь попросить: выдать выход на сцену,
   пустить в VIP. Решение и телепорт делает сервер.
4. **Косметика — только на клиенте.** Массовка, эффекты, камера, рамка 9:16 не существуют для
   сервера, поэтому не стоят ни трафика, ни тиков физики.

## Структура карты

```
Workspace
├── Stadium              — геометрия: чаша, трибуны, сцена, LED-конструкции
├── StageAnchors         — точки телепортации (обычные Part, Anchored, Transparency = 1)
│   ├── PerformerSpot    — куда ставим выступающего
│   ├── AudienceSpot     — куда возвращаем после слота
│   ├── VipSpot          — VIP-ярус
│   └── FrontRowSpot     — первый ряд
├── Lights               — SpotLight / Beam с тегом StageLight
├── Fx                   — ParticleEmitter с тегами StagePyro и StageFog
├── Screens              — SurfaceGui с TextLabel, тег StageScreen
├── CrowdZones           — Part, задающие площадь массовки, тег CrowdZone
└── Gates                — турникеты с тегами VipGate и FrontRowGate
```

Теги ставятся в Studio через окно Tags (CollectionService). Код ничего не ищет по именам
моделей, кроме `StageAnchors`, поэтому арт можно перестраивать как угодно: достаточно
сохранить теги.

### Почему теги, а не жёсткие пути

Сцену придётся переделывать много раз: другой свет, больше экранов, новая конструкция под
вертикальный кадр. Если код ищет `Workspace.Stadium.Stage.Lights.Spot07`, любая переделка
ломает шоу. С тегами художник добавляет новый прожектор, ставит `StageLight`, и он сразу
участвует в шоу.

## Серверная часть

| Модуль | Отвечает за | Ключевые решения |
| --- | --- | --- |
| `ShowDirector` | Расписание и объявление треков | Считает следующий слот расписания, объявляет старт трека с запасом `leadInSeconds`, собирает подтверждения о прогрузке, отдаёт состояние подключившимся позже |
| `StageQueue` | Открытая сцена | Очередь userId, слоты по таймеру, списание выхода в момент старта слота, кулдаун, лимит эффектов, снятие перформера при начале концерта |
| `Monetization` | Покупки | `ProcessReceipt` с идемпотентностью по `PurchaseId`, `PurchaseGranted` только после успешной записи, кэш владения геймпассом |
| `Profiles` | Хранение | Все изменения через `UpdateAsync`-дельты, поэтому покупка, выданная на другом сервере или после выхода игрока, не затирается |
| `VipAccess` | Платные зоны | Проверка владения на сервере, телепорт сервером, турникеты по тегам |
| `SafeText` | Пользовательский текст | `TextService:FilterStringAsync` + `GetNonChatStringForBroadcastAsync` для имени на экране |
| `Anchors` | Точки карты | Единая точка доступа с понятным предупреждением, если точка не настроена |

## Клиентская часть

| Модуль | Отвечает за |
| --- | --- |
| `ShowRunner` | Прогрузка и воспроизведение трека, выравнивание по общим часам, подтяжка дрейфа, выполнение кью, пульсация света по долям такта |
| `StageUI` | HUD: отсчёт до концерта, очередь, VIP, реакции зала, панель перформера с эффектами и таймером |
| `CinemaMode` | Рамка 9:16, выключение интерфейса, пять операторских планов, автоматическая смена плана по кью, нативный шаринг скриншота |
| `CrowdLod` | Локальная массовка из импостеров, дистанционный LOD, скрытие ников на расстоянии |

## Протокол

Весь обмен — через `ReplicatedStorage/ConcertNet`, создаётся автоматически модулем `Net`.

Сервер → клиент:

| Событие | Когда | Payload |
| --- | --- | --- |
| `PreloadRequest` | Перед шоу | Список `soundId` для прогрузки |
| `TrackStarted` | На каждый трек | `{showId, songId, startTime, bpm, duration}` |
| `TrackStopped` | Конец трека | `songId` |
| `StageState` | Смена перформера, очереди, режима | `{performerUserId, stageName, endsAt, queueSize, applause, open}` |
| `QueueState` | Персонально | `{position, credits, queueSize}` |
| `StageFx` | Перформер нажал эффект | Имя эффекта |
| `CrowdReaction` | Реакция зала (unreliable) | Идентификатор реакции |
| `Toast` | Сообщение игроку | Строка |
| `ShowState` | RemoteFunction | Полное состояние для подключившегося |

Клиент → сервер: `ClientReady`, `JoinStageQueue`, `LeaveStageQueue`, `BuyStageSlot`,
`SetStageName`, `PerformerFx`, `SendReaction` (unreliable), `RequestVip`, `AdminCommand`.

Правило: во время шоу новых сообщений не появляется вообще. Один `TrackStarted` на трек —
и дальше тишина. Это то, что позволяет держать полный сервер без сетевых лагов.

## Чего в каркасе нет и что придётся добавить

Каркас закрывает логику, но не арт и не несколько инфраструктурных вещей:

- **Геометрия стадиона, свет, партиклы, LED-экраны.** Весь арт делается в Studio/Blender.
- **Анимации группы и риг участников.** См. [03-music-and-show.md](03-music-and-show.md).
- **Кросс-серверные вещи:** общий счётчик зрителей по всем шардам (`MessagingService`),
  сквозная очередь или глобальный рейтинг перформеров (`MemoryStoreService`), группировка
  друзей в один инстанс (`TeleportService:ReserveServer`). Нужны, когда появится несколько
  одновременных шардов, не раньше.
- **Админ-панель.** Сейчас команды уходят через `AdminCommand` и проверяются по
  `ShowConfig.Admins`; интерфейс к ним нужно нарисовать.
- **Запись реплея.** Буфер последних 30 секунд с возможностью пересъёмки другим планом —
  сильная фича для клипов, но она требует отдельной системы и в каркас не входит.
